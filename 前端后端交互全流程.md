# PI-Light 前端-后端交互全流程文档

## 总览

本文档详细记录从"自由装配"到"配置约束"再到"实验启动"的完整交互流程，包括每一步的用户操作、前端发出的 HTTP 请求、后端返回的数据结构，以及关键架构决策。

---

## 一、架构关键决策

### 1.1 `__compatible_plugins__` 显式声明 + 缓存预计算

- 每个编排器通过 `__compatible_plugins__` 类属性声明兼容的插件白名单
- 不声明时，AST 分析编排器的 `setup()` 方法调用推导兼容性
- `COMPATIBILITY_CACHE` 在 `app` 启动时一次性预计算，避免运行时 AST 扫描/`hasattr` 检查
- 语法：`compatible = method_ok AND decl_ok`

### 1.2 编排器只能调用组件方法，不能访问组件内部属性

- 允许：`self._observer.observe(env)`
- 禁止：`ag._n_lstm`、`ag._net.state_dict()`

### 1.3 `scaffold_config()` 返回 `dict`，非 YAML 字符串

- 后端直接返回字典，需要字符串的端点自行 `yaml.dump`

### 1.4 约束展示：从语义源头构建（非 Union-Find 合并）

- `_build_display_groups()` 从四个语义源头构建独立约束组：topology、port_equation、input_match、internal_deps
- `_dim` 后缀键不在侧栏展示（由前端 `isDimKey` 过滤）
- input_match 约束组后端返回匹配状态，前端直接展示

### 1.5 `rule` 编排器不需要 collector

- `__compatible_plugins__` 声明中省略 collector，前端的组件优先路径自动排除 collector 槽位

```json
    {"id":"frap", "name":"frap", "category":"observer", "default_params":{"features":["num"],"num_phase":4,"max_lanelinks":1,...}, "dim_keys":[{"key":"observe_out_dim","label":"观测输出维度"}]},

  ],
  "algorithm": [...],
  "collector": [...],
  "reward": [...],
  "environment": [{"id":"sumo", "category":"environment", "default_params":{"sim_max_time":3600,"decision_interval":5,"yellow_duration":3,"min_green":5,"roadnet_file":"","flow_file":""}}],
```

### 3.2 路径 A：编排器优先

```
① 用户点击 "single" (编排器)
  → addModule({id:"single", category:"orchestrator"})
  → assembledModules = [{orchestrator:"single"}]
  → refreshAssemblyState()
```

**请求**：`GET /api/assemble/iterative`（无 selections 参数）

**后端**：`assembly_iterative({})`
- 所有三个编排器均可用
- Union 所有编排器的组件 options（从 `COMPATIBILITY_CACHE` 读取）
- 每个 opt 带 `viable_in` 和 `compatible` 字段

**返回数据结构**：
```json
{
  "viable_orchestrators": ["ma2c", "rule", "single"],
  "slots": {
    "observer": {
      "options": [
        {"plugin":"frap", "compatible":true, "viable_in":["ma2c","rule","single"], "missing_in":{}},
        {"plugin":"standard", "compatible":true, "viable_in":["single"], "missing_in":{"ma2c":[...],"rule":[...]}},
        ...
      ]
    },
    "algorithm": {...},
    "collector": {...},
    ...
  },
  "kinds_order": ["environment","observer","actor","reward","collector","algorithm","tracker"],
  "all_complete": false,
  "dead_end": false,
  "missing_kinds": ["environment","observer","actor","reward","collector","algorithm","tracker"]
}
```

**前端处理**：`refreshAssemblyState()` 检测到 `orch` 存在 → 重建 `assemblyState`
```javascript
// ① 过滤编排器
viable_orchestrators = ["single"]  // 收缩到选中的

// ② 重建每个 slot 的 options
for each kind in slots:
  for each opt:
    opt.compatible = opt.viable_in.includes("single")
    // 重建全新对象赋值，确保 Vue 响应式
```

**前端渲染**：
- single: ■ 绿色（已选中）
- ma2c: □ 变灰（不在 viable 中）
- rule: □ 变灰
- observer: frap ✓, standard ✓, colight ✓, ma2c ✓ (single 的 __compatible_plugins__ 包含全部)
- collector: replay ✓, ma2c ✗（不在 single 声明中）
- algorithm: frap ✓, dqn ✓, colight ✓, ma2c_agent ✓ (single 声明包含全部 DRL 算法)
- reward: composite ✓, queue ✓

```
② 用户继续点击 observer "frap"
  → assembledModules = [{orchestrator:"single"}, {observer:"frap"}]
  → refreshAssemblyState()

GET /api/assemble/iterative?selections=observer:frap

后端：
  viable = ["single","rule"]  ← ma2c 被过滤（不支持 frap observer）
  Union single + rule 的 options

前端：
  orch 存在 → 重建：compatible = viable_in.includes("single")
  → 所有组件范围进一步收缩
```

---

### 3.3 路径 B：组件优先

```
用户点击 "frap" (算法)
  → assembledModules = [{algorithm:"frap"}]
  → refreshAssemblyState()

GET /api/assemble/iterative?selections=algorithm:frap

后端：
  viable = ["single","rule"]  ← ma2c 被排出
  Union single + rule 的 options

前端：
  orch = null → assemblyState = raw（直接用 API 原文）
  isModuleAvailable("ma2c"): 不在 viable 中 → false → 变灰
  各组件按 API 返回的 compatible 显示
```

核心函数 `isModuleAvailable(module)`：
```javascript
if (module.category === 'orchestrator') {
    return state.viable_orchestrators.includes(module.id);
}
// 普通组件
const opt = slot.options.find(o => o.plugin === module.id);
return opt !== undefined && opt.compatible !== false;
```


### 4.2 用户选择数据集

```
用户点击 "Hangzhou1" 数据集
  → onDatasetSelected("Hangzhou1")
  ① selectedDataset = "Hangzhou1"
  ② 写入 env.custom_params.roadnet_file = "data/Hangzhou1/roadnet.net.xml"
  ③ 写入 env.custom_params.flow_file = "data/Hangzhou1/flow_0.rou.xml"
```

**请求**：`GET /api/assemble/dataset-topo?path=data/Hangzhou1/roadnet.net.xml`

**后端**：`get_dataset_topo()` → 返回拓扑详情
```json
{"num_phase": 6, "max_lanelinks": 16, "num_tsc": 1}
```

**前端**：显示拓扑信息面板

```
  → initConstraintSession()

POST /api/assemble/constraint-session
Body: {
  "orchestrator": "single",
  "selections": {"observer":"frap","algorithm":"frap","actor":"phase","collector":"replay","reward":"composite","environment":"sumo"},
  "dataset_path": "data/Hangzhou1/roadnet.net.xml"
}
```

**后端**：`ConstraintSession.__init__()`

**步骤 1 — 拓扑注入 (Layer 1)**：
```
find_topo("data/Hangzhou1/roadnet.net.xml") → {num_phase:6, max_lanelinks:16, num_tsc:1}
→ solver.set_value(kind, k, v) for each kind
→ add_equal("environment","num_phase", "observer","num_phase")
→ add_equal("environment","num_phase", "algorithm","num_phase")
→ add_equal("environment","max_lanelinks", "observer","max_lanelinks")
→ ...
```

**步骤 2 — PortEquation (Layer 2)**：
```
wiring edges: observer.observe → algorithm.act → actor.translate → env.step
              collector.push → algorithm.learn
              collector.pull → algorithm.sync
              env.time → tracker.log, env.ids → algorithm.eval

for each output method:
  ① resolve_port_deps(cls, method) — AST 扫描该方法的 self._xxx 属性
  ② filter_deps_by_sensitivity — 逐一扰动验证敏感性
  ③ 注册确定器 _probe_determiner(kind, cls, method, exact_deps)
  ④ add_group({(kind, dim_key), (kind, dep)}) for each dep

add_equal(fk, f"{fm}_out_dim", tk, f"{tm}_in_dim") for each wiring edge
```

**步骤 3 — 组件内部依赖 (Layer 3)**：
```
scan_setup_param_deps(cls):
  AST 扫描 setup() 中的 cfg.get(key, expr)
  例: cfg.get("reward_norm", 1.0 / self._num_phase)
      其中 self._num_phase = cfg.get("num_phase", 4)
      → {"reward_norm": {"num_phase"}}

for each target_key, dep_keys:
  add_group({(kind, target_key), (kind, d)})
```

**步骤 4 — build_display_groups()**：
```
四个语义源头:
  1. topology: member=[(env, num_phase), (env, max_lanelinks), (env, num_tsc)]
  2. port_equation: 每个 output 方法的配置依赖列表
  3. input_match: 每个 add_equal 等式 (fk.fm_out_dim ⇔ tk.tm_in_dim)
  4. internal_deps: scan_setup_param_deps 的结果
```

**返回数据结构**：
```json
{
  "session_id": "abc12345",
  "state": {
    "merged_groups": [
      {"members":[{kind:"environment",key:"@dataset",value:"data/Hangzhou1/roadnet.net.xml",topo_keys:[...]}], "label":"拓扑与维度约束", "source":"topology"},
      {"members":[{kind:"observer",key:"num_phase",value:6},{kind:"observer",key:"max_lanelinks",value:16}], "label":"observer.observe 输出依赖", "source":"port_equation"},
      {"members":[{kind:"observer",key:"num_phase",value:6}], "label":"algorithm.act 输出依赖", "source":"port_equation"},
      {"members":[], "label":"actor.translate 输出依赖", "source":"port_equation"},
      {"label":"observer.observe ↔ algorithm.act", "source":"input_match", "from_value":22, "to_value":6, "match_status":"matched"},
      {"label":"algorithm.act ↔ actor.translate", "source":"input_match", "from_value":6, "to_value":4, "match_status":"matched"},
      ...
    ],
    "values": {
      "observer": {"num_phase":6, "max_lanelinks":16, "observe_out_dim":22},
      "algorithm": {"num_phase":6, "max_lanelinks":16, "act_in_dim":22},
      ...
    },
    "unknown_count": 5,
    "warnings": []
  }
}
```

**前端**：
```javascript
constraintSessionId = "abc12345"
constraintState = response.state

// ① syncResolvedValuesFromState()
//    → 把后端求解的值写回模块的 custom_params/dim_params
//    → observer.custom_params["num_phase"] = "6"（输入框自动填充）
//    → observer.custom_params["max_lanelinks"] = "16"
//    → algorithm.custom_params["num_phase"] = "6"

// ② submitInitialConfigValues()
//    → 遍历每个模块的 custom_params
//    → 如果在约束组中 → POST set-value 提交默认值
//    → 后端 solver 获取完整数据 → 等式传播 → 自动求解 dim_keys
//    → syncResolvedValuesFromState() → 再次写入求解结果
```

### 4.3 侧栏约束组渲染

前端模板分三种渲染模式：

**模式 1 — input_match 约束组**：
```html
<div v-if="group.source === 'input_match'">
  <span>{{ match_status === 'matched' ? '✅' : ... }}</span>
  <span>{{ group.label }}</span>
  <span>
    已匹配 (22 = 22) / 不匹配 (22 ≠ 6) / 待解析
  </span>
</div>
```

**模式 2 — 有可见成员的约束组**：
```html
<div v-else-if="visibleMembers(group).length > 0">
  标题: {{ getConstraintGroupLabel(group) }}
  进度: {{ getConstraintGroupProgressText(group) }}  <!-- (2/3) -->
  <div v-for="member in visibleMembers(group)">
    {{ member.kind }}.{{ member.key }} = {{ member.value }}
  </div>
</div>
```

**模式 3 — 空成员的约束组（零 dep 的 port_equation）**：
```html
<div v-else>
  ✅ {{ label }} 无需配置参数
</div>
```

**`isDimKey` 过滤器**：
```javascript
function isDimKey(kind, key) {
    if (key.endsWith('_in_dim') || key.endsWith('_out_dim')) return true;
    // 也检查 dim_keys 列表
}
```
所有 `_in_dim`/`_out_dim` 后缀的计算维度不被展示。

### 4.4 用户修改配置参数

```
用户改 algorithm.num_phase: 6 → 8
  → onConfigParamChange(algorithmModule, "num_phase")
  → isKeyInAnyGroup("algorithm", "num_phase") → 穿透 @dataset.topo_keys
  → notifyDimChange("algorithm", "num_phase", 8)
```

**请求**：`POST /api/assemble/constraint-session/{id}/set-value`
```json
{"kind": "algorithm", "key": "num_phase", "value": 8}
```

**后端**：`ConstraintSession.set_value()`
```
solver.set_value("algorithm", "num_phase", 8)
solver.solve():
  → equal: observer.num_phase(6) != algorithm.num_phase(8) → 冲突
  → warning: "conflict: (observer.num_phase=6) != (algorithm.num_phase=8)"
```

**返回**：
```json
{
  "delta": {
    "warnings": ["conflict: (observer.num_phase=6) != (algorithm.num_phase=8)"]
  },
  "state": { ... }
}
```

**前端**：
```javascript
constraintState = response.state
syncResolvedValuesFromState()
// → algorithm.custom_params["num_phase"] = "8" (确认)
// → constraintState.warnings 包含冲突消息
```

**冲突联动**：
- 侧栏 input_match 组：`⚠️ 不匹配 (6 ≠ 8)` + 红色边框
- 侧栏 topology 组：红色边框
- 配置卡片 algorithm.num_phase：输入框红色边框 + 标签变红
- 冲突警告区域显示详细消息

### 4.5 同步流程闭环

```
          ┌──────────────────────────────────────────────────────────────────┐
          │                         constraintState                           │
          │   merged_groups[]   values{}   warnings[]                         │
          └──────┬───────────────────┬───────────────────────────────────────┘
                 │                   │
  visibleMembers()         syncResolvedValuesFromState()
  isDimKey() 过滤          写入 custom_params + dim_params
                 │                   │
                 ▼                   ▼
            侧栏约束组          中间配置卡片（el-input v-model）
            member.value        m.custom_params[key]
                 │                   │
                 │           @change → onConfigParamChange()
                 │                   │
                 └── notifyDimChange() ←───┘
                            │
               POST set-value → solver.solve() → get_state()
                            │
                            ▼
                    constraintState 更新 → Vue 重新渲染
```

### 5.2 启动实验

**步骤 ②**：`POST /api/experiments/start_custom`
```json
{
  "dataset_id": "Hangzhou1",
  "gui_enabled": false,
  "config": { /* 上一步返回的完整配置 */ }
}
```

**后端**：`start_custom_experiment()`
1. 校验路网/车流文件存在性
2. 写入临时 YAML 文件
3. 启动后台线程运行 `run_experiment()`
   - `Launcher(config_path).build()` — 三层求解 (Layer 1/2/3)
   - `orch.run()` — warmup + training epoch loop
   - `find_topo()` — 多级路径匹配（绝对→相对→尾部）
   - `_build_orch()` — 单独 algorithm 包装为 list

```
Launcher 关键限制：
  - algorithm 配置为 dict 时 → 构建单个对象 → _build_orch 包装为 [obj]
  - algorithm 需要 list 参数（SingleOrchestrator.setup(algorithms: list)）
```
