# PI-Light 前端设计文档

## 文档版本

v2.0 / 2025-05-06

---

## 一、概述

### 1.1 设计理念

PI-Light 前端将强化学习交通信号控制实验的构建过程类比为**硬件模块的组装体验**，并提供四个入口覆盖三类用户的需求：探索者（"这平台能做什么"）、构建者（"我有新算法要测试"）、分析者（"我要跑对比实验"）。

底层共享同一套 API：
```
list_all / recommend_assembly / filter_orchestrators_by_plugin / scaffold --yaml / py -m modutsc run
```

### 1.2 核心概念

| 概念 | 类比 | 说明 |
|------|------|------|
| 模块 | 硬件元件 | 一个已注册的插件实现，如 `DqnAlgorithm`、`StandardObserver` |
| 编排器 | 训练范式 | 决定组件如何交互、何时被调用、训练如何递进 |
| 装配槽 | PCIe 插槽 | 一个必选或可选的位置，填入模块后形成完整方案 |
| 约束传播 | 匹配提示 | 每做一次选择，所有未选模块的可选范围实时刷新 |
| 出站 | 组装完成 | 全部必选槽填满后，一键生成 YAML 配置文件并启动实验 |

### 2.1 入口一：快速开始

**目标用户**：探索者——"我想看看这平台能做什么"。

**行为**：点击"开始体验" → 自动加载预置的 `dqn_monaco.yaml` → 后台调 `py -m modutsc run` → 1-2 分钟后在界面上看到训练曲线（reward × episode、queue × episode）。

**用户感知**：零配置，一键出图。激发"我也想改"的冲动后，自然跳转到"自由装配"。

### 3.2 左侧：模块货架

每个 模块 构成一个可折叠的货架分区。模块卡片显示图标、名称、一行描述。

**卡片状态**：

| 状态 | 样式 | 说明 |
|------|------|------|
| 可选 | 白色背景 | 可点击/可拖拽 |
| 不兼容 | 灰色背景 + 灰色文字 | 不可选，悬浮显示原因 |
| 已选 | 蓝色边框高亮 | 右上角 x 可取消 |

**不兼容原因气泡**：

```
┌───────────────────────────────────────┐
│ ? 不兼容原因                          │
│                                       │
│ 已选算法 DQN 期望输入类型: np.ndarray │
│ igrl_graph 输出类型: DGLHeteroGraph   │
│                                       │
│ 建议更换为: standard / frap / colight │
└───────────────────────────────────────┘
```

### 3.3 中央：装配工作台

按拓扑顺序排列的插槽链。顺序由 `recommend_assembly` 返回的 `order` 字段确定。

**插槽状态**：

| 状态 | 图例 |
|------|------|
| 已填充 | `│ observer standard ? │` 蓝色边框 |
| 待填充（必选） | `│ algorithm (必选) │` 红色虚线空槽 |
| 待填充（可选） | `│ tracker (可选) │` 灰色虚线空槽 |
| 无兼容项 | `│ collector (无兼容项) │` 红色实线边框 |

**交互**：
- 拖拽：从货架拖模块到插槽
- 点击空槽：弹出兼容列表
- 取消：点击已填充槽的 x
- 悬停连线：显示依赖说明

### 3.5 约束传播规则

```
用户选择模块 M(kind=K, name=N):

Step 1 —— 编排器过滤:
   如果 K != "orchestrator":
     compatible_orchs = filter_orchestrators_by_plugin(K, N)
     如果之前已选编排器 O 且 O 不在 compatible_orchs 中:
       → 冲突! 弹窗提示

Step 2 —— 推荐范围刷新:
   对每个 compatible_orch 调 recommend_assembly(orch_name)
   对每个未选 kind: 可选项 = 所有 compatible_orch 的 by_kind[kind]["options"] 的交集
   更新货架灰色/亮色状态

Step 3 —— 已选模块一致性检查:
   对每个已选模块: 如果不在当前可选项中 → 自动取消或提示用户
```

## 四、交互流程

### 4.1 完整流程

```
首页 → 选择入口
  │
  ├── 快速开始 → 加载预置 YAML → 启动实验 → 看曲线 → [进入装配修改]
  │
  ├── 论文复现 → 浏览论文卡片 → 一键复现 → 看结果 → [保存/修改]
  │
  ├── 自由装配 → VM-Studio:
  │      │
  │      任意起点选择模块 → 约束传播 → 剩余模块收缩
  │      → 再选 → 再收缩 → 全部必选槽填满
  │      → 生成配置 → 下载 YAML / 直接启动
  │
  └── 实验矩阵 → 勾选变体 → 预览组合 → 生成全部 YAML → 下载 ZIP
```

### 4.2 冲突处理

**编排器冲突**：用户先选算法 `ma2c_agent` 再选编排器 `rule` → 弹窗显示原因 → 选择取消哪一方。

**模块冲突**：用户已选模块不再出现在兼容列表中 → 自动从工作台移除。

## 五、API 接口卡片

前端通过以下四个函数驱动全部交互：

| # | API | 参数 | 返回 | 调用时机 |
|---|-----|------|------|---------|
| 1 | `list_all(kind=None)` | `kind="observer"` 或 `None` | `["standard","frap",...]` 或全部 `[(k,n),...]` | 界面初始化 |
| 2 | `filter_orchestrators_by_plugin(kind, name)` | `("algorithm","dqn")` | `["single","rule"]` | 用户选了非编排器模块时 |
| 3 | `recommend_assembly(orchestrator_name)` | `("single")` | `{order, by_kind, required_kinds}` | 用户选了编排器 / 约束传播刷新 |
| 4 | `scaffold --yaml <path> --plugin <k> <n> ...` | CLI 调用 | YAML 文件内容 | 生成配置 |
| 5 | `py -m modutsc run <path>` | CLI 调用 | 训练输出 | 启动实验 |

### API #3 返回结构

```python
{
    "orchestrator": "single",
    "required_kinds": ["environment","observer","actor","reward","collector","algorithm"],
    "order": ["observer","actor","reward","collector","algorithm","environment"],
    "by_kind": {
        "observer": {
            "required": True,
            "options": ["standard","frap","colight","ma2c","igrl_graph"],
            "depends_on": []
        },
        "algorithm": {
            "required": True,
            "options": ["dqn","frap","colight","igrl","ma2c_agent"],
            "depends_on": ["observer","actor"]
        }
    }
}
```
